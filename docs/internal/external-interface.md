# Внешний интерфейс Оркестратора

Что Оркестратор «выставляет наружу» и как этим **правильно** пользоваться из
дашбордов, автоматизаций, blueprint'ов датчиков и внешних систем.

Границы ответственности (важно с самого начала):

- **Оркестратор** владеет сущностями режима/управления/гейтов, событиями и
  сервисами — это и есть его внешний интерфейс (ниже).
- **`ha-lighting-compilers`** владеет **топологией и групповыми светильниками**:
  Floors, Areas, метки, групповой свет этажей (Area с меткой `ba_floor_area`) и
  помещений (`light.<room>_obshchii`). Оркестратор их *читает* и *управляет*
  сервисными вызовами по `area_id`, но не создаёт. **Что генератор обязан
  обеспечить — см. §9** (метки, инвариант Area, покрытие агрегата этажа).
- **`zone_manager`** владеет **датчиками движения** и их автоматизациями —
  Оркестратор их *разрешает/запрещает* через гейт, но не создаёт.

> **Никаких `input_boolean`/хелперов Оркестратор не создаёт.** Legacy
> `input_boolean.regim_auto_<N>` заменён полноценной сущностью `switch` (см. §3).
> **opt-out помещений — тоже не метка**, а политика в `.storage` Оркестратора
> (правится в панели): генератору метку `ba_optout` ставить **не нужно**.

## 1. Обзор: одно устройство, четыре класса сущностей

Интеграция создаёт **одно устройство** «Оркестратор здания». Все сущности
привязаны к нему.

| Уровень | Сущность | Тип | Запись | Назначение |
|---|---|---|---|---|
| Здание | режим управления | `select` | **да** | Авто / Ручной для всего здания |
| Здание | режим расписания | `sensor` | нет | текущий вычисленный режим |
| Здание | отложенный переход | `sensor` | нет | целевой режим (атрибут `apply_at`) |
| Здание | источник доступен | `binary_sensor` | нет | доступность источника расписания |
| Этаж (на каждый) | автоматика этажа | `switch` | **да** | ON = следует расписанию, OFF = ручной стоп |
| Этаж (на каждый) | датчики (**гейт**) | `binary_sensor` | нет | цель fail-open для автоматизаций датчиков |
| Этаж (на каждый) | применённый режим | `sensor` | нет | режим, применённый на этаже |

**Актуальные `entity_id` (пример с объекта):**

```
select.orkestrator_zdaniia_rezhim_upravleniia_zdaniem          режим здания
sensor.building_automation                                     режим расписания
sensor.orkestrator_zdaniia_otlozhennyi_perekhod               отложенный переход
binary_sensor.orkestrator_zdaniia_istochnik_raspisaniia_dostupen  источник доступен
switch.orkestrator_zdaniia_avtomatika_etazh_1_etazh           автоматика эт. 1
switch.orkestrator_zdaniia_avtomatika_etazh_2_etazh           автоматика эт. 2
binary_sensor.orkestrator_zdaniia_datchiki_razresheny_etazh_1_etazh  гейт эт. 1
binary_sensor.orkestrator_zdaniia_datchiki_razresheny_etazh_2_etazh  гейт эт. 2
sensor.orkestrator_zdaniia_primenennyi_rezhim_etazh_1_etazh   применённый эт. 1
sensor.orkestrator_zdaniia_primenennyi_rezhim_etazh_2_etazh   применённый эт. 2
```

> ⚠ **`entity_id` зависит от установки.** Он генерируется из русского имени и
> может отличаться на другом объекте или после ручного переименования. Стабилен
> `unique_id`, но ссылаться в YAML/blueprint приходится по `entity_id`. Отсюда
> правило: **зафиксировать `entity_id` гейтов на объекте один раз** и обновлять
> ссылки при переименовании (см. §2).

## 2. Гейт датчиков — главный контракт наружу

Гейт этажа (`binary_sensor …_datchiki_razresheny_etazh_<N>`) — то, ради чего
Оркестратор существует для системы датчиков. Значения: `on` — датчики включены,
`off` — выключены.

**Читать только шаблоном `!= 'off'` (fail-open):**

```yaml
condition:
  - condition: template
    value_template: "{{ states('binary_sensor.orkestrator_zdaniia_datchiki_razresheny_etazh_1_etazh') != 'off' }}"
```

Почему именно так, а не `condition: state … 'on'`:

- **Оркестратор недоступен / гейт исчез** (выгрузка интеграции, рестарт) →
  состояние `unknown`/`unavailable`/отсутствует → `!= 'off'` даёт **истину** →
  датчики **продолжают работать**. Освещение не «залипает» из-за Оркестратора.
- `condition: state` с целевым `'on'` дал бы обратное (fail-**closed**): нет
  гейта → условие ложно → датчики отключаются. **Так нельзя.**

**Правила:**
- Гейт — **только чтение**. Не писать в него, не подменять.
- Одна автоматизация датчика читает гейт **своего этажа**.
- Гранулярность гейта — **этаж** (не помещение). Датчики помещения следуют гейту
  этажа.

## 3. Управление режимом Авто/Ручной

Два пути, оба разрешены **любому авторизованному пользователю** (не только
администратору):

**Сущностями напрямую** (для дашбордов, кликабельных бейджей):

```yaml
# этаж: тумблер (ON = следует расписанию, OFF = ручной стоп)
service: switch.turn_off
target: { entity_id: switch.orkestrator_zdaniia_avtomatika_etazh_1_etazh }

# здание: выбор Авто/Ручной
service: select.select_option
target: { entity_id: select.orkestrator_zdaniia_rezhim_upravleniia_zdaniem }
data: { option: "manual" }   # auto | manual
```

**Сервисом** (для скриптов/автоматизаций; цель — здание или этаж):

```yaml
service: building_automation.set_control_mode
data:
  target: floor        # building | floor
  mode: manual         # auto | manual
  floor_id: "1_etazh"  # обязателен при target: floor
```

Возврат в Авто **догоняет текущее расписание сразу** (не восстанавливает
устаревший режим).

> **Не писать в `.storage` Оркестратора напрямую** и не мутировать его сущности в
> обход — только через сервисы/сущности выше. Профили правятся в панели
> (WS-команды, §6), а не подменой файла.

## 4. Мониторинговые сущности (только чтение)

Для дашбордов, истории, шаблонов:

- `sensor …_rezhim_raspisaniia` (`sensor.building_automation`) — режим расписания:
  `lesson` / `break` / `window` / `off`.
- `sensor …_primenennyi_rezhim_etazh_<N>` — реально применённый режим этажа.
- `sensor …_otlozhennyi_perekhod` — целевой режим отложенного перехода; атрибут
  **`apply_at`** — момент применения (монотонное время, не настенные часы; для
  «через сколько» не годится как абсолютная метка).
- `binary_sensor …_istochnik_raspisaniia_dostupen` — `on`, если источник
  расписания доступен.

**Состояние — источник истины.** Стройте мониторинг и историю на **состояниях
сущностей**, а не на событиях (§5): подписчик, поднявшийся позже Оркестратора,
события не получит.

## 5. События на шине

Импульсы для **реактивных** автоматизаций и MQTT-моста. Не для построения
состояния (см. §4).

| Событие | Payload |
|---|---|
| `building_automation_mode_changed` | `new_mode`, `previous_mode`, `source` |
| `building_automation_mode_warning` | `target_mode`, `apply_at` |
| `building_automation_transition_cancelled` | `cancelled_mode` |

События **здания-широкие** (без `floor_id`/`area_id`). Пример подписки:

```yaml
trigger:
  - platform: event
    event_type: building_automation_mode_changed
```

---

## 6. WebSocket-команды (в основном для панели)

Панель пусконаладчика общается с ядром только через WS-команды с префиксом
`building_automation/` (чтение — любому, правка профилей — администратору). Их
можно вызывать и программно (`hass.callWS`), но это **внутренний контракт панели**
(SPEC §2.6), а не рекомендованный публичный API. Для внешних потребителей —
сущности, события и сервисы выше.

Полный список и права — в [`SPEC.md` §2.6](../SPEC.md).

---

## 7. MQTT-трансляция (опция)

Разрешена **retained-публикация текущего режима** (на объекте уже используется
`khimki/mode_work` внешними системами). Это трансляция **состояния**.

> **Управление оборудованием по MQTT запрещено** (граница §2.3 ТЗ). MQTT — только
> «сказать наружу, какой сейчас режим», не «включить свет по MQTT».

---

## 8. Чего не делать (сводка антипаттернов)

- ❌ Читать гейт как `state == 'on'` (fail-closed) — только `!= 'off'` (§2).
- ❌ Писать в гейт или другие read-only сущности.
- ❌ Писать в `.storage` Оркестратора в обход панели/сервисов (§3).
- ❌ Строить мониторинг/историю из событий вместо состояний (§4).
- ❌ Управлять оборудованием по MQTT (§7).
- ❌ Жёстко полагаться на `entity_id`, не зафиксировав их на объекте (§1).
- ❌ Управлять групповыми светильниками `ves_N`/`*_obshchii` в обход
  Оркестратора, ожидая согласованности режимов, — это его зона (профили каскада).

## 9. Что Оркестратор ожидает от топологии (контракт с генератором)

Оркестратор топологию **не создаёт** — читает из реестра HA. Чтобы каскад
работал корректно, `ha-lighting-compilers` должен обеспечить:

**Метки на Area:**

| Метка | На что | Зачем |
|---|---|---|
| `ba_floor_area` | агрегатная Area этажа (одна на этаж) | по ней Оркестратор находит групповой свет этажа для схлопывания |
| `ba_type_<тип>` | помещение | профили по типу привязываются к нему; значения: `class`, `korridor`, `recreation`, `zal`, `special`, `hall` |

> `ba_optout` генератору ставить **не нужно** — opt-out ведёт Оркестратор в
> `.storage` (решение Q3=C).

**Инвариант Area:** в каждой Area помещения — **ровно один** световой объект
(`light.*`). Ноль или несколько → помещение **пропускается** (`no_light` /
`multiple_lights` в мониторинге), профиль к нему не применяется. Групповые
светильники помещений (`light.<room>_obshchii`) должны быть привязаны к своим
Area именно так.

**Покрытие агрегата этажа — гарантирует генератор.** Световой объект агрегатной
Area этажа (с меткой `ba_floor_area`) должен управлять **объединением
светильников всех помещений этажа**. Оркестратор при однородном этаже схлопывает
каскад в один вызов по `area_id` агрегатной Area и **доверяет** этому покрытию —
проверить его изнутри он не может (членство групп живёт во внешнем конфиге
генератора, не в реестре HA). **Нарушение = часть помещений молча не
переключится.** Это ключевой инвариант на стороне генератора.

Полный контракт (форма гейта в blueprint'ах, порядок внедрения) —
[`contract-ha-lighting-compilers.md`](contract-ha-lighting-compilers.md).

# Генератор `zone_manager.json`

> ✅ **Реализовано 2026-07-23** (шаги 1–6). Закрыт последний крупный долг —
> «система собрана, но свет не включится без JSON Zone Manager». Осталась
> приёмка на объекте (см. ROADMAP, «Zone Manager»). Документ описывает формат
> и правила сборки; ниже — статус по шагам.

## Что это

`zone_manager.json` — конфигурация, которую blueprint'ы датчиков запрашивают
через `zone_manager.get_sensor_config`. Без неё автоматизация получает
`found: false` и свет не включается. Интеграция —
[github.com/Azrielshka/zone_manager](https://github.com/Azrielshka/zone_manager).

Раньше собиралась вручную. Теперь в таблице есть источник — лист
«Группы соседей», — и файл генерируется как остальные артефакты.

## Формат листа «Группы соседей»

- **Forward-fill**: «Основной датчик» и «Основная группа света» заполнены только
  в первой строке блока; строки ниже с пустым основным датчиком **продолжают**
  его, добавляя ещё по одному соседу.
- **Позиционные тройки**: каждая строка блока даёт один элемент в
  `neighbors` / `neighbor_groups` / `far_neighbors` (связаны по позиции).
- Одна ячейка = один адрес (не список через запятую).

| Колонка | Поле JSON |
|---|---|
| Основной датчик (`1.22.1`) | ключ `zones.<sensor.ms_*>` |
| Основная группа света (`413_1`) | `light_group` |
| Соседние датчики | `neighbors` |
| Соседние группы света | `neighbor_groups` |
| Дальние соседние датчики | `far_neighbors` |

## Целевой JSON

```
{
  "version": "v0.1",
  "spaces": {
    "NAME SPACE": { ... },              # захардкоженный эталонный блок
    "<Название помещения>": {
      "zones": {
        "sensor.ms_X_Y_Z": {
          "light_group":     ["light.*"],
          "neighbors":       ["sensor.ms_*"],
          "far_neighbors":   ["sensor.ms_*"],
          "neighbor_groups": ["light.*"]
        }
      }
    }
  }
}
```

`light_group_single` в файл НЕ кладём — его интеграция вычисляет сама из
`light_group` при ответе на `get_sensor_config`.

## Правила

**Датчик:** `X.Y.Z` → `sensor.ms_X_Y_Z` (канон `sensor_motion_entity`).

**Группа света** (одинаково для основной и соседних):
- `103_1` (цифры_цифры) → зонная `light.103_1`;
- `101_Тамбур` (имя помещения) → общая `light.<room_slug>_obshchii`.

Различение — по формату и сверке с реальными group_id / именами помещений из
«Проектной БД».

**Заглушки** — зона без соседей / без дальнего:
`sensor.ms_zaglushka`, `light.l_zaglushka`.

**Пустая ячейка vs явный маркер** (различаем на валидации):
- явный `-` / `None` / `нет` (`is_none_token`) → намеренно нет → **заглушка**;
- пустая ячейка (`is_blank`) там, где ждём значение → **ошибка** «пропуск?».

**Группировка `spaces`:** «Название помещения» из «Проектной БД» по адресу
основного датчика (сырое имя, как «Коридор 413»).

## Почему заглушка и дубль соседа в far работают одинаково

В OFF-скрипте `motion_near_off_json.yaml` `far` читается только внутри ветки,
где ближний сосед уже НЕ `motion`:

```
near == motion  → skip
иначе:  far == motion → подождать 30с
        иначе        → гасить сразу (0)
```

Заглушка никогда не `motion` → «гасить сразу». Дубль соседа: мы уже в ветке
«near ≠ motion», far = тот же датчик → тоже ≠ motion → та же ветка. Результат
идентичен. Ставим заглушку — она чище и явно говорит «дальнего нет».

## Reload после деплоя (решено)

После деплоя нового файла интеграция сама его **не перечитает** (в blueprint
`get_sensor_config` идёт с `reload: false`). Деплой сервисы не трогает и HA не
перезапускает (политика), поэтому после отправки файла он **печатает
напоминание** вызвать `zone_manager.reload` (или `get_sensor_config` с
`reload: true`). Наладчик делает это вручную — иначе конфиг молча не вступит
в силу.
